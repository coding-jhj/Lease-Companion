# 실전 계약 점검 UI·서비스 화면 검증 (2026-07-27)

첫 전월세 계약을 준비하는 20대 후반 임차인 관점으로 실전 계약 점검 흐름의 화면을 점검한 결과다.

## 검증 방법과 한계

- **방법**: `frontend/src` 화면·feature·라우터·스타일 코드 정독, 관련 Backend 검증 규칙(`backend/app/schemas/auth.py`, `backend/app/core/errors.py`) 대조.
- **한계**: 로컬 앱을 띄워 실제 조작한 결과가 아니다. 실기기 렌더링·터치 반응·실제 응답 지연은 확인하지 않았다. 아래 항목은 모두 코드 근거를 병기했으며, 실검증 절차는 [`docs/testing/real-contract-validation.md`](../testing/real-contract-validation.md)를 따른다.
- **대상 범위**: `/choose-mode` → `/start` → `/prepare` · `/contracts/*` (1~7단계). 계약 연습(`/practice`)은 이번 범위에서 제외했다.

## 가정한 사용자

- 27세, 첫 전월세 계약. 계약서 초안을 카톡 PDF로 받았고, "등기부등본"이라는 말은 들어봤지만 "등기사항증명서"라는 명칭에는 익숙하지 않다.
- 대부분 **휴대폰**으로 접속한다. 계약서 PDF를 옆에 띄워 두고 한 항목씩 대조한다.
- 알고 싶은 것은 단 하나: **"지금 당장 뭘 해야 하지?"**

## 잘 되어 있는 점 (유지)

- 단정 표현 회피 원칙이 화면 문구까지 일관되게 지켜진다. "안전"·"위험"·"사기 점수"가 없고 `반드시 확인 / 확인 권장 / 일반 확인`을 문구·아이콘(`!` `?` `i`)·색을 함께 써 표현한다. (`features/judgment-results/PriorityGroups.tsx:10-16`)
- 모바일 대응 CSS가 실제로 촘촘하다. 767px 이하에서 확인 카드 1열, 헤더 액션 44px 터치 타깃, 업로드 제출 버튼 하단 안전영역(`env(safe-area-inset-bottom)`)까지 처리돼 있다. (`styles/global.css:1047-1113`)
- 로딩/오류/빈 데이터 상태가 `AsyncState` 3종으로 통일돼 있고 오류 문구가 "저장된 계약 정보는 변경되지 않았습니다"처럼 **데이터 안전을 먼저 알린다.** 첫 사용자의 불안을 정확히 겨냥한 문구다.
- 시연용 서비스 안내와 개인정보 미업로드 경고가 업로드 화면 상단에 있다. (`pages/document-upload/DocumentUploadPage.tsx:121-128`)
- `/prepare`(계약서 없는 경우) 화면의 "가계약금 보내기 전 요청 문구 복사"는 첫 계약자가 바로 쓸 수 있는 실용적 산출물이다.

## 개선 필요 항목

우선순위는 **첫 계약자가 실제로 손해를 보거나 이탈하는 정도** 기준이다.

### P0-1. 4단계 확인 내용이 새로고침 한 번에 전부 사라진다

- **근거**: `pages/extraction-review/ExtractionReviewPage.tsx:130-151`. `drafts`·`reviewedKeys`·`unresolvedReasonByKey`·`situation`이 전부 컴포넌트 로컬 state다. 서버 저장은 마지막 `confirm()`(:434) 한 번에서만 일어난다. 재진입 시 `loadExtraction()`이 복원하는 것은 서버의 `verification_status`뿐이다(:245-280).
- **사용자 경험**: 계약서 PDF와 대조하며 20~30개 항목을 확인하는 데 10~20분이 걸린다. 그 사이 카톡 알림을 눌러 앱을 벗어났다 돌아오거나(모바일 탭 폐기), 새로고침하거나, 헤더의 "처음으로"를 누르면 **입력한 수정값과 확인 표시가 전부 초기화된다.** 경고도 없다.
- **왜 치명적인가**: 이 화면이 전체 흐름에서 가장 오래 머무는 화면이고, 여기서 날아가면 대부분 다시 하지 않는다.
- **개선안**
  1. (최소) 이탈 경고: 확인 중인 변경분이 있을 때 `beforeunload`와 라우터 이탈 확인. 헤더 "처음으로"·"로그아웃"에도 적용.
  2. (권장) 구역(`ReviewSection`)을 넘길 때마다 그 구역의 수정값을 기존 `submitCorrections` API로 부분 저장. API 신설 없이 현재 계약을 그대로 쓸 수 있다.

### P0-2. 5단계 지연 화면의 버튼 두 개가 동작이 같다

- **근거**: `pages/analysis-progress/AnalysisProgressPage.tsx:167-168`. `계속 기다리기`와 `다시 확인`이 모두 `retry()`를 호출한다.
- **사용자 경험**: "계속 기다리기"를 눌렀는데 실제로는 재확인이 돌고, 두 번 눌러도 같은 일이 반복된다. 첫 사용자는 "내가 뭘 잘못 눌렀나" 또는 "이거 고장났나"로 읽는다.
- **개선안**: 버튼을 하나(`다시 확인`)로 줄이고, 문구를 "서버가 아직 만들고 있어요. 잠시 후 다시 확인해 주세요."로 통일한다. 자동 재시도를 유지하려면 "계속 기다리기"는 버튼이 아니라 진행 중 상태 문구여야 한다.

### P0-3. 회원가입 아이디 규칙이 화면에 없어 첫 관문에서 막힌다

- **근거**: Backend는 아이디를 `^[A-Za-z0-9_]+$`, 3~30자로 검증한다(`backend/app/schemas/auth.py:8`). 프론트 가입 폼에는 비밀번호 규칙 안내만 있고 아이디 규칙 안내가 없다(`pages/auth/AuthPage.tsx:62-65`).
- **여기에 더해**: 422 응답 메시지는 `"입력값이 올바르지 않습니다."` 한 줄이다(`backend/app/core/errors.py:39`). 필드별 `details`는 내려오지만 `AuthPage`는 `caught.message`만 표시한다(:31).
- **사용자 경험**: 한글 아이디나 `.`이 든 아이디를 넣으면 **무엇이 왜 틀렸는지 알 수 없는** 한 줄만 뜬다. 서비스 첫 화면에서의 이탈은 회복이 안 된다.
- **개선안**: 아이디 입력 아래 `field-hint`로 "영문·숫자·밑줄 3~30자" 표기 + `pattern` 속성 추가. 추가로 `ApiError.details`의 `loc`를 해당 입력 필드 아래에 매핑해 표시.

### P1-1. 중개대상물 확인설명서를 올릴 수 없다 (타입만 존재)

- **근거**: `UploadDocumentType`·Backend `DocType`·업로드 페이지의 `initialFiles`/`initialStatuses`/`initialErrors`에 `"중개대상물 확인설명서"`가 모두 정의돼 있으나(`pages/document-upload/DocumentUploadPage.tsx:19-33`), 화면에 렌더되는 `DocumentUploadCard`는 계약서·등기사항증명서 2개뿐이다(:132-155). "어떤 문서인가요?" 설명 목록에도 빠져 있다(:116-119).
- **사용자 경험**: 중개사에게 확인설명서를 받아 왔는데 올릴 자리가 없다. 반면 결과 리포트의 체크리스트는 "중개대상물 확인·설명서의 내용을 확인하고 사본을 교부받으세요"라고 안내한다(`features/question-cards/actionNormalization.ts:25`). **받으라고 해놓고 낼 곳이 없다.**
- **개선안**: 둘 중 하나로 정리한다 — (a) 세 번째 선택 카드를 노출하거나, (b) 미지원이면 죽은 상태값 3벌을 지우고 타입에서도 제외한다. 현재처럼 절반만 남겨 두지 않는다.

### P1-2. "N개 모두 네, 맞아요"가 금전 항목까지 한 번에 통과시킨다

- **근거**: `ExtractionReviewPage.tsx:201-205, 671-685`. `bulkConfirmItems`는 구역 종류를 가리지 않는다. "금전 피해로 이어질 수 있는 내용"(보증금·계좌·잔금) 구역에서도 동일한 묶음 버튼이 뜬다.
- **사용자 경험**: 카드 요약에 보이는 값은 한 줄이고, 데스크톱 폭에서는 `text-overflow: ellipsis; white-space: nowrap`으로 잘린다(`styles/global.css:254`). 즉 **보증금 뒷자리가 잘린 상태로 "모두 맞아요"를 누를 수 있다.** 첫 계약자는 빨리 넘기고 싶어서 누른다.
- **개선안**: 금전 구역(`money_direct`)에서는 묶음 확인을 제공하지 않거나, 묶음 확인 전에 해당 값 전체를 펼쳐 보여주는 확인 단계를 둔다. 최소한 요약 줄의 말줄임을 금액 필드에서는 풀어야 한다.

### P1-3. "문서에서 확인하기 어려워요"를 되돌릴 방법이 안 보인다

- **근거**: `features/extraction-review/GuidedReviewCard.tsx:194-222`. 이유를 고르면 `onCannotVerify`가 호출되고 `markCannotVerify`가 해당 항목을 `reviewedKeys`에서 빼고 `unresolvedReasonByKey`에 넣는다(`ExtractionReviewPage.tsx:369-372`). 카드에는 "역시 확인했어요"에 해당하는 되돌리기 버튼이 없다.
- **실제로는** "직접 고칠게요" → 같은 값 저장 경로로 우회 복구가 되지만(`changeCurrent`가 unresolved를 지운다), 사용자가 이 경로를 발견할 이유가 없다. `mode`도 `cannot-verify`로 남아 이유 선택 라디오가 계속 붙어 있다.
- **추가**: 라디오에 `checked` 바인딩이 없어(비제어) 구역을 옮겼다 돌아오면 어떤 이유를 골랐는지 화면에 남지 않는다. 상태는 저장돼 있는데 표시가 없다.
- **개선안**: `cannot-verify` 모드에 "취소" 버튼 추가, 라디오를 `unresolvedReasonByKey` 값으로 제어, 카드 상태 문구를 "확인하지 못함 · 문서에 적혀 있지 않음"처럼 이유까지 표기.

### P1-4. 4단계 상단 진행률이 실제 진행과 어긋난다

- **근거**: 상단 진행바는 `reviewedKeys`만 센다(`ExtractionReviewPage.tsx:176, 623-636`). 반면 구역별 카운트와 완료 판정(`allHandled`)은 "확인 불가"로 표시한 항목도 처리 완료로 센다(:162-167, 182-184).
- **사용자 경험**: 흐린 스캔본을 올려 여러 항목을 "확인하기 어려워요"로 넘기면, **구역 표시는 5/5이고 완료 화면까지 뜨는데 상단 진행바는 0%에 가깝게 남는다.** "다 했는데 왜 0이지?"
- **개선안**: 두 카운트의 분모·분자 기준을 하나로 맞춘다. 확인 불가를 진행에 포함하되 색을 달리하거나(예: 회색 구간), 진행바 라벨을 "확인 20 · 확인 불가 4 / 전체 24"로 분해 표기한다.

### P1-5. 오류 문구에 개발자 용어가 그대로 노출된다

- **근거**: `services/apiClient.ts:28-32, 50-52`. 네트워크 실패와 5xx에서 `"Backend 실행 상태를 확인한 뒤 다시 시도해 주세요."`가 사용자에게 그대로 표시된다. 미디어 경로도 동일하다(:83).
- **사용자 경험**: "Backend"가 뭔지 모른다. 자기 잘못이라고 느끼거나 서비스를 신뢰하지 않게 된다.
- **개선안**: 사용자 문구는 "지금 서버에 연결할 수 없습니다. 잠시 후 다시 시도해 주세요."로 바꾸고, 개발자용 진단 문자열은 콘솔·에러 코드로만 남긴다.

### P2-1. 파일 형식·용량 오류 시 선택한 파일이 통째로 지워진다

- **근거**: `pages/document-upload/DocumentUploadPage.tsx:56-63`. 검증 실패면 `files[docType]`을 `null`로 되돌린다.
- **사용자 경험**: 20MB를 넘는 스캔 PDF를 고르면 파일명조차 남지 않고 "파일 선택하기"로 되돌아간다. 무엇을 골랐다가 실패했는지 흔적이 없어 같은 파일을 다시 고르기 쉽다.
- **개선안**: 파일명은 남기고 카드를 `error` 상태로 유지한다. 오류 문구에 대안을 함께 준다 — "휴대폰으로 촬영한 사진(JPG)으로 나눠 올려도 됩니다."

### P2-2. "PDF 저장" 버튼이 실제로는 인쇄 대화상자다

- **근거**: `pages/result-report/ResultReportPage.tsx:118-123`, `pages/contract-detail/ContractDetailPage.tsx:210-215`. `window.print()` 호출이다.
- **사용자 경험**: 모바일 크롬·사파리에서는 인쇄 시트가 뜨고, "PDF로 저장"을 다시 찾아 눌러야 한다. 라벨과 실제 화면이 달라 잠시 멈춘다.
- **개선안**: 라벨을 "인쇄 · PDF로 저장"으로 바꾸거나, 버튼 옆에 "인쇄 화면에서 'PDF로 저장'을 선택하세요" 한 줄을 둔다. 코드 변경은 문구 한 줄이면 된다.

### P2-3. 7단계 하단에 계약 삭제 버튼이 그대로 노출된다

- **근거**: `pages/contract-detail/ContractDetailPage.tsx:483-490`. "대시보드로 돌아가기" 바로 아래에 전체 폭 `danger-button`이 놓인다. 대시보드에서는 같은 기능이 `details`("계약 관리") 안에 접혀 있다(`pages/dashboard/DashboardPage.tsx:44-53`).
- **사용자 경험**: 모바일에서 아래로 스크롤해 "대시보드로 돌아가기"를 누르려다 삭제를 누를 수 있다. `window.confirm`이 막아 주지만, 두 화면의 위험도 표현이 다른 것 자체가 일관성 문제다.
- **개선안**: 대시보드와 동일하게 접힌 "계약 관리" 안으로 옮긴다.

### P2-4. "이전 분석 항목 (item_key)"이 내부 식별자를 그대로 보여준다

- **근거**: `pages/contract-detail/ContractDetailPage.tsx:137-148`. 생성 결과에 없는 과거 체크 상태를 `이전 분석 항목 (${item.item_key})`로 표시하고 `writable: false`, 체크 자리에 `✕`(변경 불가)를 둔다.
- **사용자 경험**: 뜻 모를 영문 키가 체크리스트에 섞여 있고 누를 수도 없다. 첫 사용자는 "오류인가?"로 읽는다.
- **개선안**: 문구를 "이전 확인 결과에서 저장한 항목 (지금은 수정할 수 없어요)"로 바꾸고 원문 키는 `details` 안으로 넣거나 제거한다.

### P2-5. "등기사항증명서"에 통용 명칭 병기가 없다

- **근거**: `pages/document-upload/DocumentUploadPage.tsx:118, 146-147`.
- **사용자 경험**: 대상 사용자 다수가 "등기부등본"으로 알고 있다. 명칭이 다르면 "내가 가진 건 이게 아닌가 보다"라고 판단해 업로드를 건너뛴다. 등기 문서가 없으면 교차검증 판정이 대거 "확인 불가"가 되므로 리포트 가치가 크게 떨어진다.
- **개선안**: 카드 제목 옆에 "(등기부등본)" 병기, 설명에 "인터넷등기소에서 700원에 발급받을 수 있어요" 수준의 획득 경로 한 줄 추가.

### P3-1. 1단계 화면들만 진행 표시가 사라진다

- **개선안**: `/start`에 `step="1 / 7"`을 부여해 시작부터 전체 분량을 보여준다. (여정 정의상 이미 1단계로 매핑돼 있으므로 라우팅 변경은 불필요하다.)

### P3-2. 헤더 로고가 모드와 무관하게 실전 계약 대시보드로 간다

- **근거**: `components/layout/PageShell.tsx:157`. 브랜드 링크가 항상 `/contracts`다. 계약 연습 화면에서도 마찬가지다.
- **개선안**: 로고는 `/choose-mode`로 보내거나, 현재 모드에 맞는 홈으로 분기한다.

### P3-3. 결과 리포트에 쓰이지 않는 앵커가 남아 있다

- **근거**: `features/judgment-results/PriorityGroups.tsx:133, 162`이 `first-priority-group`·`first-action-item` id를 붙이지만, 저장소 어디에서도 이 id를 참조하지 않는다(링크·스크롤 호출 없음).

- **개선안**: 둘 중 하나 — 리포트 히어로에 "가장 먼저 확인할 항목 보기" 버튼을 달아 앵커를 살리거나, 쓰지 않을 것이면 두 줄을 지운다. 지금처럼 반쯤 남겨두지 않는다.

# 추가 검증: 처음 쓰는 사람이 겪는 이해·조작 부담

앞 목록은 **고장·불일치**를 다뤘다. 이 절은 코드가 의도대로 동작하더라도 **첫 사용자가 이해하지 못하거나, 힘들어서 그만두는 지점**을 다룬다. 항목 번호는 `U-`로 구분한다. 검증 방법과 한계는 문서 앞부분과 같다(코드 정독 기반, 실행 검증 아님).

## U-1. (P0) 확인 화면에 "그 값이 계약서 어디에 있는지"가 없다

- **근거**
  - `SourceEvidenceDto { page, text }`가 모든 추출 필드에 붙어 온다(`types/api.ts:77-80, 88`). 그러나 저장소 전체에서 `source_evidence`를 화면에 그리는 곳이 없다. `GuidedReviewCard`는 값과 프롬프트만 보여준다(`features/extraction-review/GuidedReviewCard.tsx:123-145`).
  - 원본 문서를 앱 안에서 열 수단도 없다. `mvpService`에 문서 내려받기·미리보기 호출이 없고(`services/mvpService.ts:53`의 `getDocuments`는 메타데이터만 반환), 계약 상세는 파일명만 나열한다(`pages/contract-detail/ContractDetailPage.tsx:476-478`).
- **사용자 경험**: 4단계는 "계약서와 같은지 확인해 주세요"라고 요구한다. 그런데 비교 대상인 계약서가 화면에 없고, **어느 쪽에서 읽은 값인지도 알려주지 않는다.** 휴대폰 사용자는 항목 하나마다 카톡·파일앱으로 나갔다가 돌아와야 한다. 20~30개 항목이면 앱 전환 수십 회다. 이 왕복 자체가 P0-1(작업 소실)의 발생 확률을 직접 끌어올린다.
- **참고**: 계약 연습 모드에는 대화 옆에 계약서 본문을 띄우는 2열 작업 화면이 이미 있다(`practice-simulation-workspace`, `styles/global.css:694-710`). 정작 진짜 계약서를 봐야 하는 실전 모드에 그 화면이 없다.
- **개선안**
  1. (최소·즉시) `source_evidence.page`가 있으면 카드에 "계약서 2쪽에서 읽었어요" 한 줄, `text`가 있으면 읽은 원문 조각을 인용으로 표시. 데이터는 이미 내려오므로 렌더 코드만 추가하면 된다.
  2. (권장) 문서 내려받기 엔드포인트를 붙여 확인 화면에서 업로드한 PDF·사진을 함께 볼 수 있게 한다. 넓은 화면은 2열, 모바일은 접었다 펴는 형태.

## U-2. (P1) 이미 작성돼 있는 항목별 안내가 화면에 하나도 안 나온다

세 벌의 설명이 코드에 준비돼 있으나 **어느 것도 렌더되지 않는다.**

| 준비된 내용 | 위치 | 화면 노출 |
|---|---|---|
| 항목별 확인 요령 12개 (`reviewGuidance`) | `features/extraction-review/viewModel.ts:60-74` → 뷰모델 `guidance`(:274) | 없음 |
| 값이 비어 있는 이유 (`failure_reason`) | 같은 파일 :247, :261에서 설정 | 없음 |
| 원문 위치·원문 조각 (`source_evidence`) | `types/api.ts:77-80` | 없음 (U-1) |

- **사용자 경험**: 예를 들어 관리비 칸이 비어 있으면 사용자는 "AI가 못 읽었나?"로 읽는다. 정답("사용량·세대수 등에 따라 산정되어 문서에 고정 관리비 금액이 없습니다")은 이미 작성돼 있는데 화면에는 일반 문구 "문서에 안 적혀 있어요"만 뜬다(`features/extraction-review/reviewQueue.ts`의 `fieldReasons`). 예금주 칸도 마찬가지로 "계좌번호만 있고 예금주가 없으면 송금 전에 임대인 본인 명의인지 직접 확인하세요"라는 문장이 준비돼 있으나 보이지 않는다.
- **개선안**: `guidance`와 `failure_reason`을 `GuidedReviewCard`의 `item.reasons` 영역에 함께 출력한다. 새 문구를 쓸 필요가 없어 작업량 대비 효과가 가장 큰 항목이다.

## U-3. (P1) 금액이 원 단위 숫자로만 표시돼 검증이 어렵다

- **근거**: `formatFieldValue`가 숫자에 `toLocaleString("ko-KR")`만 적용한다(`features/extraction-review/viewModel.ts:224-234`). 단위 표기도, 억·만 단위 병기도 없다.
- **사용자 경험**: 보증금이 `20,000,000`으로 뜬다. 이 화면의 목적은 **자릿수 오탈자를 사용자가 잡아내는 것**인데, 정작 0의 개수를 사람이 세야 한다. 첫 계약자에게 2천만 원과 2억 원의 차이는 화면상 0 하나다. 게다가 데스크톱 폭에서는 요약 줄이 말줄임 처리된다(P1-2 참조).
- **개선안**: 금액 필드(`numericFields`)는 `2,000만 원 (20,000,000원)` 형태로 병기한다. 한글 표기 금액 필드(`deposit_korean_amount` 등)가 별도로 존재하므로, 숫자 금액과 나란히 놓아 J07(숫자·한글 표기 일치) 확인을 사용자가 눈으로 할 수 있게 하면 더 좋다.

## U-4. (P1) 항목 이름이 계약 경험자용 어휘다

- **근거**: `features/extraction-review/viewModel.ts:9-57`. 화면에 그대로 나오는 이름 중 일부 — `목적물 주소`, `선순위 권리·채권 합계`, `지상권 존재`, `신탁등기 존재`, `가압류 존재`, `위반건축물 표시`, `임대·전대 권한 확인`, `건축물 용도`.
- **여기에 더해**: `labels`에 없는 필드는 전부 `"추가 확인 항목"`이라는 **같은 이름**으로 표시된다(:267). 스키마가 늘면 화면에 이름이 똑같은 카드가 여러 개 나란히 뜨고, 사용자는 어느 것이 무엇인지 구분할 수 없다.
- **사용자 경험**: "목적물"이 자기가 계약할 집이라는 걸 모른다. "선순위 권리·채권 합계"는 이 서비스에서 가장 중요한 숫자 중 하나인데 이름만 보고는 무엇인지 알 수 없다. 앞 카드의 `reviewGuidance`(U-2)가 이 문제를 상당 부분 해결하도록 이미 작성돼 있다.
- **개선안**: 화면 이름은 쉬운 말로, 법률 명칭은 부제로 병기한다 — `계약할 집 주소 (목적물 주소)`, `내 보증금보다 먼저 받아가는 돈 (선순위 권리·채권 합계)`. 미매핑 필드는 `"추가 확인 항목"` 대신 필드명을 함께 노출해 최소한 구분되게 한다.

## U-5. (P1) 얼마나 걸리는지, 얼마나 남았는지 미리 알려주지 않는다

- **근거**
  - 3단계 업로드 화면은 다음 단계에서 확인할 항목 수를 예고하지 않는다.
  - 4단계 진행바는 화면에 들어온 뒤에야 `N개 중 M개`를 보여준다(`ExtractionReviewPage.tsx:620-637`).
  - 5단계 `AnalysisTimeline`은 4단계를 나열하지만 **소요 시간 안내가 없다**(`features/analysis-progress/AnalysisTimeline.tsx:3-8`). 실제 폴링 상한은 5분이다(`utils/pollUntilTerminal.ts:4`).
- **사용자 경험**: 4단계에서 "이거 언제 끝나지?"를 판단할 수 없어 중간에 접는다. 5단계에서는 30초만 지나도 "멈춘 거 아닌가" 싶어 새로고침하거나 뒤로 간다. 첫 사용자에게 대기 시간의 불확실성은 실패로 읽힌다.
- **개선안**: 업로드 완료 버튼 문구에 분량 예고("다음 화면에서 20여 개 항목을 확인합니다"), 5단계에 "보통 1~2분 걸립니다. 화면을 닫지 말고 기다려 주세요" 표기. 시간 수치는 로컬 실측 후 기입하고, 측정 전에는 임의 수치를 쓰지 않는다.

## U-6. (P1) 중간에 나갔던 사람이 자기 자리로 돌아오지 못한다

- **근거**: 대시보드의 이어하기 버튼은 `action_status` 하나로 목적지를 정한다(`pages/dashboard/DashboardPage.tsx:8-17`). 그런데 Backend의 `_action_status`는 **분석이 완료되고 생성 결과가 있으며 체크리스트를 체크한 개수**로만 계산된다(`backend/app/api/routes/contracts.py:47-75`).
- **결과**: 문서를 올리고 4단계 확인을 하다 나간 계약은 여전히 `none`이다. 대시보드는 그 계약에 **"점검 시작하기"**를 띄우고 `/contracts/:id/upload`, 즉 **문서 업로드 화면으로 되돌려 보낸다.** 이미 올린 문서가 있다는 사실도 그 화면에서는 보이지 않는다(업로드 카드가 항상 빈 상태로 시작).
- **사용자 경험**: 어제 하다 만 걸 이어서 하려고 들어왔는데 처음부터 다시 하라고 한다. 문서를 또 올려야 하는 줄 안다.
- **개선안**: 대시보드 라벨·목적지를 계약의 실제 진행 지점(문서 유무 → 추출 완료 여부 → 확인 완료 여부 → 분석 완료 여부)으로 분기한다. `action_status`는 이름 그대로 "체크리스트 행동 상태"이므로, 진행 단계용 값과 분리한다.

## U-7. (P2) 시작 전에 무엇을 준비해야 하는지 알려주지 않는다

- **근거**: 흐름이 `모드 선택 → 상황 선택 → 계약 이름 입력 → 문서 업로드`다. 준비물 안내는 업로드 화면에 처음 나온다(`pages/document-upload/DocumentUploadPage.tsx:110-120`).
- **사용자 경험**: 계약 이름부터 지어놓고 들어갔더니 "계약서 초안이 필요합니다"를 만난다. 등기사항증명서는 중개사에게 요청해야 얻을 수 있는 문서라 그 자리에서 구할 수 없다. 이 사용자는 빈 계약 건만 남기고 이탈한다.
- **참고**: `/prepare` 화면(계약서 없는 경우)이 이 내용을 아주 잘 다룬다. 문제는 **그 화면을 고른 사람에게만 보인다**는 점이다. "계약서 초안을 받았어요"를 고른 사람은 준비물 안내를 못 본다.
- **개선안**: 상황 선택 카드(`pages/mode-select/SituationSelectPage.tsx:12-18`)의 `points`에 준비물을 명시한다 — "준비물: 계약서 초안 · (있으면) 등기사항증명서".

## U-8. (P2) 결과 화면에서 "지금 뭘 해야 하는지"가 기본 화면이 아니다

- **근거**
  - 기본 선택 탭은 `items`(확인 항목)다(`pages/result-report/ResultReportPage.tsx:65`).
  - 사용자의 실제 질문에 가장 가까운 `stages`(단계별 행동) 탭은, 열어도 **5개 블록이 전부 접힌 상태로 시작한다**(`features/question-cards/DefenseActionHub.tsx:101-103, 262-266` — `foldable`의 `open` 초기값 `false`).
- **사용자 경험**: 탭을 눌렀는데 제목 5줄(계약 전 / 계약 중 / 잔금·입주 당일 / 계약 후 / 보관할 자료)만 보인다. 내용이 없는 화면으로 읽고 돌아 나온다. 개수 배지가 있긴 하나, 첫 사용자는 "펼쳐야 내용이 있다"를 학습하지 않은 상태다.
- **개선안**: 사용자의 계약 단계(`stageGuidance.contract_context.contract_stage`)에 해당하는 블록 하나는 펼친 채로 시작한다. 그 값은 이미 화면에 들어와 있고 히어로 문구 분기에도 쓰이고 있다(`ResultReportPage.tsx:42-46`).

## U-9. (P2) 신뢰의 근거인 공식자료가 가장 깊이 접혀 있다

- **근거**: 확인 항목 카드에서 법령 원문에 도달하려면 접힘을 3번 연다 — `자세히 보기`(`PriorityGroups.tsx:80`) → `공식자료 N건`(`EvidenceDisclosure.tsx:127-133`) → `원문 더 보기 (N줄)`(`EvidenceDisclosure.tsx:27`). 자료 출처는 네 번째 접힘(`자료 정보`)에 있다.
- **사용자 경험**: AI가 하는 말을 못 믿는 첫 사용자가 "근거가 뭔데?"를 확인하려면 3~4번 탭해야 한다. 반대로 근거 없이 만들어낸 말이 아니라는 사실은 **접기 전 화면에서는 전혀 드러나지 않는다.** 서비스의 핵심 차별점이 기본 상태에서 보이지 않는다.
- **개선안**: 카드 접기 전 줄에 `공식자료 2건` 배지를 노출하고(값은 이미 있음), 근거가 없는 항목은 `직접 확인 필요`로 표시한다. 접힘 단계는 3단계 → 2단계로 줄인다.

## U-10. (P2) 빈 화면과 오류 화면이 다음 행동을 주지 않는다

- **근거**: `EmptyState`는 제목·설명만 렌더하고 버튼 슬롯이 없다(`components/feedback/AsyncState.tsx:37-47`). 대시보드에서 계약이 0건일 때 "새 계약을 만들어 확인을 시작해 보세요"라고 안내하지만, 실제 버튼은 빈 상태 상자 밖 화면 맨 아래에 따로 있다(`pages/dashboard/DashboardPage.tsx:102, 117`).
- **사용자 경험**: 가입 직후 처음 보는 화면이 이 빈 화면이다. 하라는 행동과 누를 곳이 떨어져 있다.
- **개선안**: `EmptyState`에 선택적 액션 슬롯을 추가하고 빈 상태 안에 CTA를 넣는다. `ErrorState`에는 이미 `onRetry` 버튼이 있으므로 같은 형태로 맞추면 된다.

## U-11. (P2) 되돌릴 수 있는지 없는지를 화면이 말하지 않는다

- **근거**: 여정 되돌아가기에서 5단계(결과 준비)는 대상에서 제외된다(`components/layout/PageShell.tsx:30-42, 84-93`). 4단계 마지막 버튼은 "이 내용으로 확인 결과 준비하기"다(`ExtractionReviewPage.tsx:794`).
- **사용자 경험**: 첫 계약자는 이 버튼을 **되돌릴 수 없는 제출**로 받아들이고 누르기를 주저한다. 실제로는 `/contracts/:id/review`로 다시 들어가 재확인·재분석을 할 수 있는데, 화면 어디에도 그 말이 없다. 반대로 확인을 대충 하고 넘긴 사용자는 고칠 수 있다는 사실을 몰라 잘못된 값으로 받은 결과를 그대로 믿는다.
- **개선안**: 버튼 아래 한 줄 — "결과를 만든 뒤에도 내용을 다시 고치고 새로 확인할 수 있어요."

## U-12. (P3) 상태를 나타내는 말이 서로 겹쳐 보인다

사용자 화면에 동시에 등장하는 표현들이다.

- `확인 불가` (판정 상태 9개 중 하나)
- `적용 제외` (판정 상태)
- `확인 한계` (`EvidenceDisclosure`의 `limitations` 제목)
- `확인하지 못함` / `글자를 읽지 못함` / `내용이 불확실함` (추출 확인 상태, `viewModel.ts:137-184`)
- `지금 판단할 수 없는 항목` (`PriorityGroups.tsx:179`)

- **사용자 경험**: 다섯 가지가 다 "확인이 안 됐다"로 읽힌다. 내부적으로는 서로 다른 개념(판정 상태 / 근거 한계 / 추출 품질)이지만, 첫 사용자에게는 구분 기준이 보이지 않는다. 무엇을 자기가 더 해야 하고 무엇이 서비스의 한계인지 알 수 없다.
- **개선안**: 화면 문구를 **원인이 아니라 사용자가 할 일** 기준으로 재분류한다 — `내가 확인해야 함` / `자료를 구해야 함` / `이 계약에는 해당 없음` 3종으로 묶고, 정확한 내부 상태는 `자세히 보기` 안에 그대로 둔다(현재도 그 안에 표시되고 있다).

## U-13. (P3) 확인 중에도 로그아웃 버튼이 늘 헤더에 있다

- **근거**: `components/layout/PageShell.tsx:170`. `showLogout` 기본값이 `true`라 4단계 확인 화면 헤더에도 상시 노출된다. 모바일에서는 헤더 액션이 44px 터치 타깃으로 우측에 몰려 있다(`styles/global.css:1069`).
- **사용자 경험**: 그 자체로는 문제가 아니지만 **P0-1(중간 저장 없음)과 겹치면 한 번의 오터치로 확인 내용이 전부 사라진다.** "처음으로"도 같은 자리에 있다.
- **개선안**: P0-1의 이탈 경고를 이 두 버튼에도 적용한다. 별도 조치는 불필요하다.

## 결정이 필요한 사항

- **P2-5(등기부등본 병기)와 문서 표기 규칙 충돌**: [`docs/AGENTS.md`](../AGENTS.md)는 "공식 명칭이 필요한 경우 등기사항증명서를 사용한다(등기부등본 등 혼용 금지)"로 정한다. 이 규칙이 **문서 작성 규칙인지, 사용자 화면 문구까지 포함하는지**가 불분명하다. 첫 사용자 이해를 위해서는 화면 보조 문구에 통용 명칭을 병기하는 편이 유리하므로, 화면 문구에 한해 예외를 두는 것이 맞는지 결정이 필요하다. 결정 전까지 임의로 변경하지 않는다.
- **소요 시간 표기(U-5)**: 로컬 실측값이 없으므로 수치를 임의로 적지 않는다. `docs/testing/real-contract-validation.md` 절차로 측정한 뒤 기입한다.
